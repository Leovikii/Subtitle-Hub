# 标准字幕优化流程

## 1. 开工准备

AI agent 必须先读取全局规范、系列 `series-guide.md`（若存在）、作品 `project.yaml`、项目文档入口、项目补充规范、进度、问题清单和修改台账。若当前轮次正在等待人工反馈，再读取 `project/workspace/temp/review/` 中对应的审核报告。确认任务范围、目标集数、目标片源、基线版本和输出格式后才能改动字幕。

只有 `docs/project-guide.md` 可以补充或覆盖全局规范；当前状态只以 `docs/progress.yaml` 为准。开发者审核报告不能直接覆盖控制面，确认后的反馈必须回写规范、进度或台账。

如果任务只要求审查或诊断，只登记问题和证据，不得擅自实施修复。

新建作品时必须先完成 [作品身份与名称核验](project-identity.md)，再创建正式项目目录。属于既有系列时，还必须按 [系列用语规范](series-terminology.md) 建立或扩充系列 `series-guide.md`，完成术语差异审计后才能开始正文优化。

## 2. 来源入库

1. 原始字幕按语言和来源存入 `project/sources/subtitles/`；
2. 片源只记录发布名称和精确文件名，不保存视频、种子、磁力或下载链接；
3. 来源文件保持原貌，不在 `sources` 内清洗、重命名正文或修订时间轴；
4. 在作品唯一元数据文件 `project.yaml` 记录语言、来源性质、文件数量和用途；
5. 在项目规范中分别指定“时间轴主参考”“原语文本主参考”和“中文底稿”。

来源不能用一个笼统的“优先级”处理。时间轴、原语文本和中文译文是三个独立维度，必须分别选取证据。

## 3. 建立工作基线

- 从当前正式版本或经确认的输入生成 `project/workspace/episodes/<episode>/master.ass`。
- 工作文件不得直接链接回不可变来源或既有发布目录。
- 按 [workspace-and-artifacts.md](workspace-and-artifacts.md) 建立 `workspace/temp/` 和 `workspace/build/`；项目专用脚本、转换中间文件及未审候选不得散落到其他目录。
- 建立或更新 `docs/progress.yaml`，明确基线版本和本轮目标。
- 本轮发现但暂不处理的问题写入 `docs/issues.tsv`。

## 4. 原语核对与中文纠错

按 [source-and-translation.md](source-and-translation.md) 执行：

1. 先确认实际音轨说了什么；
2. 使用同语种原始字幕或正式台本辅助识别；
3. 再审查中文底稿是否存在错听连带错译、漏译、过译、语气偏差和术语错误；
4. 修改必须能够指向音轨、原语字幕、正式术语或画面证据；
5. 不得因为英文参考译法更顺口就覆盖日语等真正原语的含义。

## 5. 时间轴与分轴

按 [timing-and-layout.md](timing-and-layout.md) 执行。若目标视频包含内嵌字幕轨，应优先将其作为该片源的时间轴和分段参考；不得仅凭剧集标题相同就照搬其他版本时间轴。

有争议时依次检查：目标视频内嵌轨、音频波形和实际发声、镜头切换、同版本其他字幕。外部字幕只有在确认剪辑版本一致后才能参与定时。

内嵌轨优先不代表原样继承。普通数值偏差先生成候选；一旦触发 [内嵌时间轴纠错底线](timing-and-layout.md#4-内嵌时间轴纠错底线)，必须回到实际音频和画面局部重定时，复核受影响的相邻事件，并在修改台账记录判断依据。不得以“来自内嵌字幕”为由保留明显非法、重叠、不同步或不可读的时间轴。

## 6. 中文文本和双语布局

- 中文文本按 [chinese-style.md](chinese-style.md) 统一处理。
- 人名、地名、组织、舰船和技术术语优先服从系列 `series-guide.md`；项目确需不同译法时按项目覆盖流程取得用户确认。
- 中文位于上方并保持主视觉权重；副语位于下方。
- 中文与副语必须语义对应并共享起止时间。
- 不能为了容纳副语而删减中文核心含义、缩小中文到不可读或制造第三行。
- 无法在一个事件中稳定呈现时，应重新分轴，而不是继续堆叠文字。

## 7. 质量控制

依次执行：

1. 结构、编码、样式和事件合法性检查；
2. 中文与副语配对、时间一致性检查；
3. 来源覆盖、翻译、术语和标点检查；
4. 时长、间隔、阅读速度和视觉宽度候选检查；
5. 关键时间点和高风险修改的画面复核；
6. 整集回看或人工抽查，并如实记录实际覆盖范围。

数值检测默认产生候选项，不得无条件自动改轴；触发全局时间轴纠错底线后必须升级处理。发布门禁见 [quality-control.md](quality-control.md)。

## 8. 记录与审阅

每项实际修改必须写入 `docs/change-log.tsv`，至少记录集数、时间、类别、修改前后、依据和状态。批量规则修改可以共享 `batch_id`，但影响不同字幕事件时仍应保留逐事件明细。

完成一轮工作后必须：

- 更新 `docs/progress.yaml`；
- 关闭或更新 `docs/issues.tsv` 中对应问题；
- 需要人工审核时，按 [项目文档规范](project-documentation.md) 在 `project/workspace/temp/review/` 生成本轮临时审核报告；
- 明确哪些检查由机器完成，哪些由人工完成。
- 将人工确认结果回写 `project-guide.md`、`progress.yaml`、`change-log.tsv` 或 `issues.tsv`，然后清理已经关闭的审核报告及其他可重复生成产物。

## 9. 发布

按 [成品版本、命名与存档规范](release-and-packaging.md) 执行一个完整发布事务：

1. 从工作主稿生成 `project/workspace/build/` 中的候选产物；
2. 通过发布门禁，确认 `project.yaml` 已如实记录机器检查与人工检查覆盖范围；
3. 如已有当前成品，先删除更旧的 `subtitles/previous/`，再把完整的 `subtitles/current/` 直接重命名为新的 `previous/`；不得为轮换重新打包或逐文件复制；
4. 以目标视频文件名加 BCP 47 语种后缀生成完整成品集，并在每个 ASS 写入目标版本标记；
5. 把包含新 `VERSION` 的完整候选目录直接重命名为 `subtitles/current/`；任何失败都必须把刚轮换的 `previous/` 恢复为 `current/`；
6. 运行仓库打包脚本，核对稳定命名 ZIP、内置清单和逐文件校验值；
7. 更新项目进度、修改台账和仓库目录。旧版本号目录、`latest.yaml`、逐版本 `release.yaml` 与仓库内散落的校验文件均不得重新建立。
